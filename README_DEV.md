# README สำหรับทีมพัฒนา (Developer Guide)

เอกสารนี้สำหรับสมาชิกในทีม 4 คนที่พัฒนาโปรเจกต์นี้ร่วมกัน อธิบายกติกาการเขียนโค้ด โครงสร้างข้อมูล และสัญญาฟังก์ชัน (interface contract) ที่ทุกคนต้องยึดตาม

ห้ามแก้ไขสัญญาฟังก์ชันในเอกสารนี้เพียงลำพัง — หากจำเป็นต้องแก้ ให้แจ้งทีมก่อนทุกครั้ง

---

## 1. กติกาการแบ่งงาน

| สมาชิก | รับผิดชอบ | ไฟล์ที่แตะ |
|---|---|---|
| **A — Core** | สูตรคำนวณภาษีขั้นบันได, ค่าลดหย่อน, เพดาน | `config.py`, `core/calculator.py`, `core/deduction.py` |
| **B — Data** | บันทึก/โหลด .txt, ส่งออกใบสรุป, ตรวจเลขบัตร | `io_utils/storage.py`, `core/validator.py` |
| **C — UI** | เมนูหลัก, รับ input, ตารางแสดงผล, กราฟ ASCII | `main.py`, `io_utils/display.py` |
| **D — Extras + QA** | เกม/ควิซ, โหมดเปรียบเทียบ, ทดสอบทุกโมดูล, เอกสาร | `extras/`, ไฟล์ทดสอบ |

กฎสำคัญ: **โมดูลใน `core/` ห้ามมี `print()` หรือ `input()` เด็ดขาด** ทำหน้าที่รับค่าเข้า-คืนค่าออกเท่านั้น การติดต่อผู้ใช้ทั้งหมดอยู่ที่ `main.py` และ `io_utils/display.py`

## 2. การตั้งค่าโปรเจกต์

```bash
git clone <https://github.com/123456789i0/tax_system.git>
cd tax_system
git checkout -b dev-<ชื่อของคุณ>   # เช่น dev-a, dev-b
python main.py                     # รันทดสอบ
```

### กติกา Git

- ห้าม push ตรงเข้า `main` โดยเด็ดขาด
- ทำงานใน branch ของตัวเองเท่านั้น
- merge เข้า `main` เฉพาะตอนถึงจุดรวมพล (checkpoint) ที่ตกลงกันไว้
- ตั้งชื่อ commit ให้สื่อความหมาย เช่น `feat: add calc_tax bracket logic` ไม่ใช่ `update`

## 3. สัญญาฟังก์ชัน (Interface Contract)

ตารางนี้คือข้อตกลงที่ทุกคนต้องยึดตาม เพื่อให้โค้ดจากทุกคนต่อกันได้โดยไม่ต้องรอกัน หากฟังก์ชันยังไม่เสร็จ ให้ใส่ stub (เช่น `return 0` หรือ `return {}`) ไปก่อน เพื่อนร่วมทีมจะได้เรียกใช้ได้ทันที

### Core (A)

| ฟังก์ชัน | รับเข้า | คืนค่า |
|---|---|---|
| `calc_tax(net_income)` | เงินได้สุทธิ (`float`) | ภาษีที่ต้องชำระ (`float`) |
| `calc_tax_detail(net_income)` | เงินได้สุทธิ (`float`) | `list` ของ `tuple` แต่ละขั้นภาษี |
| `calc_deduction(profile)` | โปรไฟล์ (`dict`) | ค่าลดหย่อนรวม (`float`) |
| `calc_net_income(profile)` | โปรไฟล์ (`dict`) | เงินได้สุทธิ (`float`) |

### Data (B)

| ฟังก์ชัน | รับเข้า | คืนค่า |
|---|---|---|
| `validate_id(id_card)` | เลขบัตร (`str`) | `True` / `False` |
| `save_ taxpayer(profile)` |โปรไฟล์ (`dict`) | สำเร็จหรือไม่ (`bool`) |
| `load_all()` | ไม่มี | `list` ของ `dict` |
| `find_taxpayer(id_card)` | เลขบัตร (`str`) | `dict` หรือ `None` |
| `delete_taxpayer(id_card)` | เลขบัตร (`str`) | สำเร็จหรือไม่ (`bool`) |
| `export_summary(profile, tax)` | `dict`, `float` | ชื่อไฟล์ที่สร้าง (`str`) |

### UI (C)

| ฟังก์ชัน | รับเข้า | คืนค่า |
|---|---|---|
| `show_menu()` | ไม่มี | ตัวเลือกที่ผู้ใช้กด (`str`) |
| `input_number(prompt, min, max)` | ข้อความ, ช่วงค่า | ตัวเลขที่ผ่านการตรวจแล้ว (`float`) |
| `print_table(rows, headers)` | `list`, `list` | ไม่คืนค่า (แสดงผล) |
| `print_summary(profile, tax)` | `dict`, `float` | ไม่คืนค่า (แสดงผล) |
| `print_bar_chart(data)` | `list` ของ `tuple` | ไม่คืนค่า (แสดงผล) |

### Extras (D)

| ฟังก์ชัน | รับเข้า | คืนค่า |
|---|---|---|
| `run_quiz(n)` | จำนวนข้อ (`int`) | คะแนนที่ได้ (`int`) |
| `compare_plan(profile, extra)` | `dict`, `float` | ภาษีที่ประหยัดได้ (`float`) |
| `run_simulator(years)` | จำนวนปี (`int`) | สรุปผลเกม (`dict`) |

**ข้อตกลง:** ทุกฟังก์ชันที่คืนค่าเป็นจำนวนเงิน ให้คืนเป็น `float` ที่ยังไม่ปัดเศษ การปัดเศษให้ทำที่ชั้นแสดงผล (`io_utils/display.py`) เท่านั้น เพื่อไม่ให้ค่าคลาดเคลื่อนสะสมระหว่างการคำนวณ

## 4. โครงสร้างข้อมูล (Data Schema)

### โปรไฟล์ผู้เสียภาษี

```python
profile = {
    "id_card":    "1234567890123",   # str, 13 หลัก
    "name":       "สมชาย ใจดี",       # str
    "age":        35,                 # int
    "status":     "single",           # "single" / "married"
    "incomes": [                      # list ของ dict
        {"type": "เงินเดือน", "amount": 480000.0},
        {"type": "ค่าเช่า",   "amount":  60000.0},
    ],
    "deductions": {                   # dict
        "personal":  60000.0,
        "spouse":        0.0,
        "insurance": 25000.0,
        "fund":      50000.0,
    },
}
```

### กฎค่าลดหย่อน (ใน `config.py`)

ค่าลดหย่อนเขียนแบบ data-driven ไม่ฮาร์ดโค้ดเป็น if-elif กระจายทั่วโปรแกรม:

```python
DEDUCTION_RULES = {
    "personal": {"type": "fixed", "amount": 60000},
    "spouse":   {"type": "fixed", "amount": 60000},
    "child":    {"type": "per_unit", "unit_amount": 30000, "max_units": 3},
    "parent":   {"type": "per_unit", "unit_amount": 30000, "max_units": 4},
    "health_insurance": {"type": "percent_capped", "cap": 25000},
    "donation": {"type": "percent_of_net", "percent": 10},
}

RETIREMENT_GROUP = ["pvd", "rmf", "ssf"]   # เพดานรวมกันแยกต่างหาก
RETIREMENT_GROUP_CAP = 500000
```

หากต้องการเพิ่มค่าลดหย่อนประเภทใหม่ ให้เพิ่มรายการใน `DEDUCTION_RULES` เท่านั้น ไม่ต้องแก้ไขฟังก์ชันคำนวณ

### อัตราภาษีขั้นบันได (ใน `config.py`)

```python
TAX_BRACKETS = (
    # (เพดานบนของขั้น, อัตราภาษี %)
    (150000, 0),
    (300000, 5),
    (500000, 10),
    (750000, 15),
    (1000000, 20),
    (2000000, 25),
    (5000000, 30),
    (float("inf"), 35),
)
```

ใช้ `tuple` เพราะเป็นค่าคงที่ที่ไม่ควรถูกแก้ไขระหว่างโปรแกรมทำงาน

## 5. มาตรฐานการเขียนโค้ด

- ตั้งชื่อฟังก์ชันและตัวแปรเป็นภาษาอังกฤษ, `snake_case`
- ใส่ type hint ทุกฟังก์ชัน (เช่น `def calc_tax(net_income: float) -> float:`)
- คอมเมนต์เฉพาะจุดที่ตรรกะซับซ้อน ไม่ต้องคอมเมนต์ทุกบรรทัด
- ทุกฟังก์ชันใน `core/` ต้องเขียนแบบ pure function (รับเข้า-คืนค่าออก ไม่แตะไฟล์หรือหน้าจอ) เพื่อให้ทดสอบได้ง่าย
- จัดการข้อผิดพลาดด้วย `try/except` เฉพาะจุดที่รับข้อมูลจากผู้ใช้หรือเปิดไฟล์ ไม่ครอบทั้งโปรแกรมแบบเหมารวม

## 6. แผนงานและจุดรวมพล

| ช่วงเวลา | เป้าหมาย |
|---|---|
| สัปดาห์ 1 | ตกลง interface ร่วมกัน + เขียนสูตรคำนวณให้เสร็จก่อน |
| สัปดาห์ 2 | โปรไฟล์, ค่าลดหย่อน, เมนู, validator |
| สัปดาห์ 3 | จัดการไฟล์ครบวงจร (CRUD) + แยกโมดูล |
| สัปดาห์ 4 | หยุดเพิ่มฟีเจอร์ใหม่ / แก้บั๊ก / เขียนรายงาน |

**จุดรวมพลที่ 1** (สิ้นสัปดาห์ 1): รันแล้วเห็นเมนู กด 1 แล้วได้ตัวเลขภาษีออกมา (ผิดได้ แค่ต้องต่อกันติด)
**จุดรวมพลที่ 2** (สิ้นสัปดาห์ 2): กรอกข้อมูล บันทึกลงไฟล์ ปิดโปรแกรม เปิดใหม่ ข้อมูลต้องยังอยู่

รายละเอียดฉบับเต็มดูที่เอกสารแผนงานโปรเจกต์แยกต่างหาก

## 7. การประชุมทีม

ประชุมสั้น 15 นาทีทุกสัปดาห์ ตอบ 3 คำถาม:
1. สัปดาห์ที่ผ่านมาทำอะไรไปแล้ว
2. ตอนนี้ติดปัญหาอะไร
3. สัปดาห์หน้าจะทำอะไร

หากติดปัญหาเกิน 3 วัน ให้แจ้งทีมทันที อย่ารอจนใกล้ส่งงาน

## 8. Checklist ก่อน merge เข้า main

- [ ] โค้ดรันได้จริงไม่มี syntax error

- [ ] ทดสอบกับ input ที่ผิดปกติแล้ว (ค่าติดลบ, ปล่อยว่าง, ตัวอักษรแทนตัวเลข) ไม่พัง
- [ ] ชื่อฟังก์ชัน/พารามิเตอร์ตรงกับสัญญาในเอกสารนี้
- [ ] แจ้งทีมใน group chat ว่า merge แล้ว

## 9. Requirement รายไฟล์

ส่วนนี้ระบุหน้าที่ขั้นต่ำของแต่ละไฟล์ ข้อมูลที่ต้องรับ และผลลัพธ์ที่ต้องส่งต่อให้โมดูลอื่น

### ไฟล์ระดับโปรเจกต์

#### `main.py` — จุดเริ่มต้นและเมนูหลัก

- ต้องเป็น entry point ที่เริ่มทำงานด้วยคำสั่ง `python main.py`
- ต้องแสดงเมนูหลักและรับคำสั่งจากผู้ใช้ เช่น เพิ่มข้อมูล คำนวณภาษี ดูข้อมูล แก้ไข/ลบข้อมูล เปรียบเทียบแผน และเล่นควิซ
- ต้องเรียกใช้ฟังก์ชันจาก `core/`, `io_utils/` และ `extra/` แทนการเขียนสูตรคำนวณหรือจัดการไฟล์ซ้ำเอง
- ต้องตรวจสอบเมนูที่ผู้ใช้เลือก และวนกลับมาแสดงเมนูเมื่อทำงานเสร็จ
- ต้องมีทางออกจากโปรแกรมอย่างชัดเจน และไม่ปล่อยให้ input ที่ผิดทำให้โปรแกรมหยุดทำงาน

#### `config.py` — ค่าคงที่และกฎของระบบ

- ต้องเก็บ `TAX_BRACKETS` สำหรับอัตราภาษีขั้นบันได
- ต้องเก็บ `DEDUCTION_RULES` สำหรับกฎค่าลดหย่อนแบบ data-driven
- ต้องเก็บ `RETIREMENT_GROUP` และ `RETIREMENT_GROUP_CAP`
- ค่าที่ใช้เป็นกฎกลางต้องไม่ถูกแก้ไขระหว่างการทำงานโดยโมดูลอื่น
- ห้ามมี `input()`, `print()` หรือ logic ที่ทำให้เกิดผลข้างเคียง

### โฟลเดอร์ `core/`

#### `core/__init__.py` — package ของตรรกะหลัก

- ใช้ประกาศให้ `core` เป็น Python package
- อาจส่งออกชื่อฟังก์ชันสาธารณะที่จำเป็นได้ แต่ไม่ควรมีตรรกะการคำนวณหรือการทำงานตอน import

#### `core/calculator.py` — การคำนวณภาษี

- ต้องมี `calc_tax(net_income) -> float` คำนวณภาษีตาม `TAX_BRACKETS`
- ต้องมี `calc_tax_detail(net_income) -> list` คืนรายละเอียดเงินได้ในแต่ละขั้น อัตราภาษี และภาษีของขั้นนั้น
- ต้องมี `calc_net_income(profile) -> float` คำนวณเงินได้รวม หักค่าลดหย่อน และไม่ให้เงินได้สุทธิต่ำกว่า 0
- ต้องเรียกใช้ `calc_deduction()` จาก `core/deduction.py` ไม่คัดลอกกฎค่าลดหย่อนมาไว้ในไฟล์นี้
- ต้องรองรับเงินได้สุทธิเป็น 0 และต้องจัดการค่าติดลบตามกติกาที่กำหนดโดยระบบ
- ทุกฟังก์ชันต้องเป็น pure function และห้ามแตะไฟล์ หน้าจอ หรือรับ input โดยตรง

#### `core/deduction.py` — การคำนวณค่าลดหย่อน

- ต้องมี `calc_deduction(profile) -> float`
- ต้องอ่านประเภทค่าลดหย่อนจาก `profile["deductions"]` และใช้กฎจาก `config.DEDUCTION_RULES`
- ต้องรองรับค่าลดหย่อนแบบ fixed, per-unit และ percent-capped
- ต้องจำกัดจำนวนหน่วยตาม `max_units` และจำกัดกลุ่มกองทุนเกษียณตามเพดานรวม
- ต้องไม่ให้ค่าลดหย่อนติดลบ และต้องคืนค่าเป็น `float` ที่ยังไม่ปัดเศษ
- ต้องไม่ใช้ `print()`, `input()` หรืออ่าน/เขียนไฟล์

#### `core/validator.py` — ตรวจสอบข้อมูลผู้เสียภาษี

- ต้องมี `validate_id(id_card) -> bool` ตรวจเลขบัตรประชาชนให้เป็นตัวเลข 13 หลักและผ่าน checksum
- ควรมีฟังก์ชันตรวจสอบข้อมูลโปรไฟล์ เช่น ชื่อ อายุ สถานภาพ รายได้ และค่าลดหย่อน หากชั้น UI ต้องใช้การตรวจแบบรวม
- ต้องคืนผลตรวจสอบที่ชัดเจน และไม่แก้ไขข้อมูลต้นฉบับ
- ต้องไม่ใช้ `print()` หรือ `input()`; ข้อความแจ้งผู้ใช้ให้จัดการที่ `main.py` หรือ `io_utils/display.py`

### โฟลเดอร์ `io_utils/`

#### `io_utils/__init__.py` — package ของ input/output

- ใช้ประกาศให้ `io_utils` เป็น Python package
- ไม่ควรมี logic ที่ทำงานทันทีเมื่อ import

#### `io_utils/storage.py` — จัดเก็บและค้นหาข้อมูล

- ต้องมี `save_taxpayer(profile) -> bool` เพิ่มหรือปรับปรุงข้อมูลในไฟล์ถาวร
- ต้องมี `load_all() -> list[dict]` โหลดข้อมูลทั้งหมด และคืน `[]` เมื่อยังไม่มีไฟล์หรือข้อมูล
- ต้องมี `find_taxpayer(id_card) -> dict | None`
- ต้องมี `delete_taxpayer(id_card) -> bool`
- ต้องมี `export_summary(profile, tax) -> str` สร้างไฟล์สรุปและคืนชื่อไฟล์
- ต้องใช้รูปแบบข้อมูลที่อ่านกลับได้อย่างสม่ำเสมอ `.txt`
- ต้องตรวจเลขบัตรซ้ำก่อนบันทึก และควรเรียก `validate_id()` ก่อนเขียนข้อมูล
- โมดูลนี้รับผิดชอบไฟล์เท่านั้น ไม่ควรแสดงเมนูหรือรับ input จากผู้ใช้

#### `io_utils/display.py` — รับ input และแสดงผล

- ต้องมี `show_menu() -> str` แสดงเมนูหลักและคืนตัวเลือกของผู้ใช้
- ต้องมี `input_number(prompt, min, max) -> float` รับตัวเลข ตรวจรูปแบบ และตรวจช่วงจนกว่าจะถูกต้อง
- ต้องมี `print_table(rows, headers)` แสดงข้อมูลแบบตารางที่อ่านง่าย
- ต้องมี `print_summary(profile, tax)` แสดงข้อมูลผู้เสียภาษี เงินได้ ค่าลดหย่อน เงินได้สุทธิ และภาษี
- ต้องมี `print_bar_chart(data)` แสดงกราฟ ASCII โดยไม่ทำให้โปรแกรมพังเมื่อข้อมูลว่าง
- เป็นชั้นเดียวที่รับผิดชอบข้อความสำหรับผู้ใช้และการปัดเศษจำนวนเงินเพื่อการแสดงผล

### โฟลเดอร์ `extra/`

#### `extra/__init__.py` — package ของฟีเจอร์เสริม

- ใช้ประกาศให้ `extra` เป็น Python package
- ไม่ควรมีการทำงานหรือรับ input ทันทีเมื่อ import

#### `extra/quiz.py` — เกมควิซภาษี

- ต้องมี `run_quiz(n) -> int` เล่นควิซจำนวน `n` ข้อและคืนคะแนนที่ได้
- ต้องโหลดคำถามจาก `data/questions.txt` ด้วยรูปแบบข้อมูลที่กำหนดให้ชัดเจน
- ต้องตรวจคำตอบที่ผู้ใช้กรอกและนับคะแนนเฉพาะคำตอบที่ถูกต้อง
- ต้องรองรับกรณีไฟล์คำถามว่าง อ่านไม่ได้ หรือจำนวนข้อที่ขอมากกว่าจำนวนข้อจริง
- การแสดงคำถามและรับคำตอบควรแยกจาก logic ตรวจคะแนนเพื่อให้ทดสอบได้ง่าย

### โฟลเดอร์ `data/`

#### `data/questions.txt` — แหล่งข้อมูลคำถามควิซ

- ต้องเก็บคำถาม ตัวเลือก คำตอบที่ถูก และคำอธิบาย โดยใช้รูปแบบเดียวกันทุกข้อ
- ต้องมีข้อมูลเพียงพอสำหรับ `run_quiz(n)` และต้องระบุ encoding ที่ใช้ให้ชัดเจน
- ห้ามเก็บข้อมูลผู้เสียภาษีหรือข้อมูลลับในไฟล์นี้

#### `data/taxpayer.txt` — แหล่งเก็บข้อมูลผู้เสียภาษี

- ต้องเก็บโปรไฟล์ผู้เสียภาษีตาม schema ในหัวข้อ 4
- ต้องรองรับการเพิ่ม แก้ไข ค้นหา และลบข้อมูลโดยไม่ทำให้รายการอื่นสูญหาย
- ต้องไม่บันทึกข้อมูลที่ไม่ผ่านการตรวจสอบเลขบัตรหรือ schema
